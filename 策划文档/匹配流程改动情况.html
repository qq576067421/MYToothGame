1. 文档目的

本文档记录当前塔防从模式选择到结算返回的完整规则，用于策划、客户端和真机测试共同核对功能。

已实现 代码链路已经存在，并通过静态编译。

需要真机验收 依赖骨骼、摄像头、人脸识别或原生选择界面，无法仅靠编辑器确认最终表现。

不在当前范围 策划示意图等纯表现资源，本轮不处理。

2. 完整流程总览

  1. 玩家进入塔防入口并选择模式。
  2. 章节模式继续选择主题或关卡，无尽模式直接进入人数选择。
  3. 人数选择界面选择 1 人、2 人、3 人或 4 人。
  4. 准备界面只显示所选人数对应的 Player0 至 Player3。
  5. 每个玩家依次完成站位绑定、人脸识别、角色选择和举手准备。
  6. 所有指定人数都准备完成后，准备界面提交正式战斗请求。
  7. 战斗请求成功后才将 SDK 从准备识别切换为战斗识别。
  8. loading_wnd 完全覆盖后关闭大厅选择窗口并加载战斗。
  9. 战斗结束后先经过 1 秒结算过渡，再打开结算界面。
  10. 结算界面可继续挑战、重新挑战或返回大厅。

3. 大厅窗口层级与返回

3.1 窗口打开顺序

已实现
  • 模式选择、章节选择、人数选择和准备界面按顺序打开。
  • 进入战斗前不主动关闭前面的选择窗口，便于遥控返回逐层关闭。
  • 只有 __ParticipateCurrentActiveWindow = true 的业务窗口参与当前顶层窗口判断。
  • tip_wnd、loading_wnd 等辅助窗口不抢占业务返回层级。
主要代码： lobby_main_wnd.cs、CGamePro_Lobby.cs、UIManager.cs

3.2 大厅遥控返回

已实现
  • 在准备界面按返回，关闭准备界面并回到人数选择。
  • 在人数选择按返回，回到上一个模式或关卡选择界面。
  • 只有退到 lobby_main_wnd 后再次返回，才进入原大厅返回登录流程。
  • loading_wnd 正在覆盖或切换场景时屏蔽返回输入，避免流程竞态。

3.3 不处理的表现资源

不在当前范围

左右挥手切换角色和举手准备的示意图片由界面资源单独维护，本轮不新增。

4. 人数选择

已实现
  • 支持选择 1 人、2 人、3 人、4 人。
  • 选择 1 人时使用 Player0。
  • 选择 2 人时使用 Player0、Player1。
  • 选择 3 人时使用 Player0、Player1、Player2。
  • 选择 4 人时使用全部四个位置。
  • 人数写入 BattleStartupRequest.m_PreparePlayerCount，准备界面和战斗读取同一份数据。
  • 重新选择人数时，清空上一轮玩家、SDK 槽位和角色选择结果。
编辑器允许手动点击座位进行调试。真机禁止手点座位，人数和位置由准备阶段 SDK 识别结果决定，并且不显示编辑器座位选中状态。
主要代码： tower_defend_player_count_wnd.cs、CGamePro_Lobby.cs、tower_defend_prepare_wnd.cs

5. 准备阶段状态机

准备阶段每个座位独立维护以下状态，每个步骤不可跳过：

  1. WaitCenter：等待玩家进入对应区域。
  2. FaceRecognizing：只对已绑定的骨骼编号执行人脸识别。
  3. WaitRaiseHand：人脸阶段完成，等待举手准备。
  4. Ready：玩家已准备完成。

5.1 进入区域并绑定骨骼

已实现，需要真机验收
  • 系统按所选人数建立对应数量的检测区域。
  • 玩家稳定进入对应区域后，绑定唯一骨骼编号。
  • 已被其他座位绑定的骨骼编号不会重复分配。
  • 准备阶段玩家离开当前区域或进入其他玩家区域时，释放原准备座位并回到步骤一。
  • 这里的区域重置只属于准备阶段，不等同于战斗阶段的控制权规则。

5.2 人脸识别

已实现，需要真机验收
  • 没有玩家时，头像显示 NoPlayer，提示“请进入人脸识别区域”。
  • 玩家进入后，提示“正在识别人脸”。
  • 自动识别只处理已经绑定到当前座位的骨骼编号。
  • 自动识别最长等待 5 秒。
  • 识别成功后保存 userId，头像优先加载 avatarUri，失败后再加载 facePhotoPath。
  • 自动识别超时或失败后显示 SystemPlayer，并进入举手准备阶段。
  • 人脸头像是否选择成功不阻塞角色切换、举手准备和进入战斗。
语言编号： td_prepare_face_enter_area、td_prepare_face_recognizing、td_prepare_face_wait_avatar_select、td_prepare_face_select_avatar

5.3 人工选择头像

已实现，需要真机验收
  • 每个有效玩家位置的 head 是可操作按钮。
  • 编辑器不打开原生头像选择功能。
  • 真机点击或通过遥控器确认 head 后，调用 SDK 人工头像选择。
  • 同一时间只允许一个玩家进入人工选择，其他玩家等待当前选择结束。
  • 选择成功后，将 SDK 返回的账号头像显示到对应 head。
  • 选择失败或取消时返回准备界面并保持当前头像；没有有效头像时继续使用 SystemPlayer。
  • 人工选择不会修改准备状态。
  • 不挂载也不修改 SDK 的 HeadImageController，当前游戏使用独立的 tower_defend_prepare_face_controller。

5.4 角色选择

已实现，需要真机验收
  • 每次进入准备界面时，按座位顺序分配不同初始角色。
  • 四个角色配置完整时，四个座位初始为四个不同角色。
  • 角色不限制唯一性，不同玩家可以选择相同角色。
  • 左挥手选择上一个角色，右挥手选择下一个角色。
  • btnLeft 和 btnRight 同样可以切换角色。
  • 当前挥手速度参考值为每秒 0.7 倍肩宽，低于阈值的慢速收手不应触发反向切换。
  • 角色图标读取角色配置，不再写死只开放第 1、3 个角色。

5.5 举手准备

已实现，需要真机验收
  • 只有人脸阶段完成后才检测举手准备。
  • 手腕需要超过头部，并保留约 0.05 倍肩宽的高度余量。
  • 需要连续满足 30 个识别帧才完成准备。
  • 举手过程中 Fill 从 0 平滑增加到 1。
  • 未准备显示 noPrepare 底图，准备完成后切换为已准备状态。
  • 当前规则要求所选人数全部准备，不能只由其中一人开始游戏。
主要代码： AndroidParseDataDemo.cs、tower_defend_prepare_wnd.cs

6. 遥控器菜单选中状态

已实现
  • LUIButton 通过 ChooseState 保存自己的选中节点。
  • 遥控菜单统一调用 LUIButton.SetAsChooseState()，不再使用 Transform.Find("choose")。
  • 准备界面在 OnOpen 后根据本局人数动态绑定有效的 head 按钮。
  • 选择 2 人时只允许遥控器在两个有效头像按钮间移动，不会进入隐藏的第 3、4 个位置。
  • 所有 _wnd.prefab 中按钮直属的 choose 节点均已绑定到对应 LUIButton。
主要代码： LUIButton.cs、RenderAPI.cs、WindowBase.cs、tower_defend_prepare_wnd.cs

7. 准备数据提交与战斗切换

已实现
  • 准备界面把“战斗座位到 SDK 槽位”的绑定写入 BattleStartupRequest。
  • 真机提交时按 GetReadySeatIds() 重建正式玩家列表。
  • 正式玩家数量必须等于人数选择结果。
  • SDK 槽位绑定必须完整且不能重复。
  • 绑定错误使用语言编号 td_error_prepare_sdk_binding_missing，不显示代码中的中文明文。
  • SDK 检测到全部准备时只通知业务尝试开战，不提前停止准备识别。
  • 只有 StartBattleFromRequest() 成功后，才调用 EnterBattleWithConfirmedPlayers() 切换到战斗识别。
  • 开战校验失败时，准备检测仍保持运行，不会出现界面仍在但无法继续识别的状态。

8. Loading 与界面关闭

已实现，需要运行时验收
  • 进入战斗、结算继续和返回大厅都先打开 loading_wnd。
  • loading_wnd 最少保持 2.5 秒，以覆盖约 2 秒的铺满动画。
  • 准备界面和前面的选择窗口不会在加载遮罩铺满前关闭。
  • 场景和第一波怪物预热完成后，战斗入口才允许关闭加载界面。
  • 加载状态屏蔽空格、确认和返回等非界面输入，避免重复切换。

9. 战斗阶段骨骼控制权

已实现，需要真机验收
  • 战斗开始时优先使用准备阶段确认的骨骼编号初始化每个战斗座位。
  • 战斗阶段一旦绑定骨骼编号，不再因人物左右移动或跨越准备区域而释放控制权。
  • 只要当前骨骼编号仍被识别，角色持续由该玩家控制。
  • 连续丢失超过 30 个骨骼帧后才释放控制权。
  • 释放后允许画面中的新骨骼编号接管空座位。
  • 原玩家重新进入时，也可以和其他新玩家一样参与空座位绑定。
  • 1 人战斗重绑时使用完整画面区域，不要求玩家站在原来的左侧或右侧。
主要代码： BattleBoneParseData.cs、TowerDefendBattleScene.cs

10. 战斗内玩家实时画面

已实现，需要真机验收
  • 战斗 HUD 按“战斗座位到 SDK 槽位”绑定实时摄像头画面。
  • 不依赖准备界面关闭后失效的节点引用。
  • 每个可见 PlayerSlot 使用自己的 headView 显示对应玩家。
  • 当前默认显示模式为 Head。
  • 当前默认跟随模式为 IndependentUICamera。
  • 画面可配置为全身、上半身或头部，但当前业务默认使用头部。
  • 玩家离开并由其他骨骼接管后，实时画面跟随新的战斗骨骼编号更新。
  • 战斗实时画面与准备阶段静态账号头像是两套独立功能。
主要代码： tower_defend_battle_hud_wnd.cs、BattleHeadCameraTracker.cs

11. 结算过渡

已实现
  • 战斗满足结束条件后不立即打开结算界面。
  • 战斗流程进入独立的结算过渡状态并等待 1 秒。
  • 等待结束后才生成并显示章节或无尽结算界面。
主要代码： TowerDefendBattleProcess.cs

12. 结算继续、重新挑战与举手操作

已实现，需要真机验收
  • 结算继续按钮始终显示。
  • 章节胜利显示“继续挑战”。
  • 章节失败显示“重新挑战”。
  • 胜利时重新进入准备界面，并使用下一关。
  • 当前关已经是最后一关时，继续挑战会重新准备并重复最后一关。
  • 失败时重新进入准备界面，并重复当前关。
  • 无尽模式继续时重新进入准备界面，并重复当前无尽入口。
  • 继续和重新挑战都会重新执行人数对应的完整准备流程，不复用上一场的准备完成状态。
  • imgRaise 始终随继续按钮显示。
  • 结算界面识别到连续举手动作后，执行与继续按钮相同的行为。

13. 结算返回

已实现
  • 章节和无尽结算的 btn_return 都返回 lobby_main_wnd。
  • 点击返回后先打开 loading_wnd，等待遮罩铺满，再关闭结算界面、停止战斗并加载大厅。
  • 在结算界面按遥控返回键时，直接调用当前结算窗口的返回入口。
  • 结算遥控返回与 btn_return 完全一致，不会打开 tower_defend_setting_wnd。
  • 加载切换过程中屏蔽重复返回，避免结算窗口提前关闭或触发第二条流程。
  • 普通战斗过程中按遥控返回仍打开暂停设置界面，不受结算返回规则影响。
主要代码： tower_defend_chapter_result_wnd.cs、tower_defend_endless_result_wnd.cs、CGamePro_Scene.cs

14. 状态清理

已实现，需要重复进入验收
  • 正常退出准备界面时清理人脸头像协程、运行时纹理和事件订阅。
  • 非进入战斗的关闭会重置 SDK 准备状态。
  • 进入战斗时保留已确认骨骼编号，供战斗初始化。
  • 重新进入准备界面时重新初始化为未准备，不沿用上一轮 Ready、Fill 或头像加载请求。
  • 旧头像异步请求通过座位版本校验，玩家离开后到达的旧结果不会覆盖 NoPlayer。
